# Swagger / OpenAPI 文档转换工具：导出文档规范（框架）

> 文档状态：草案  
> 版本：0.1  
> 最后更新：2026-08-25

## 1. 通用规则

- 默认文件名：`{API标题}_{版本}_{导出日期}.{扩展名}`；缺失标题时使用 `api-document`。
- 所有文档应标注生成时间、来源规范版本和工具版本。
- 优先使用规范中的 `summary`、`description`、`example`；没有时保持为空，不臆造业务内容。
- 仅导出用户已选 Tag/接口及其关联数据模型；数据模型被多个接口引用时可去重展示。
- Schema 出现循环引用时，展示引用名与路径，不无限展开。
- 示例仅从 Swagger/OpenAPI 规范中的 `example`、`examples`、`default` 或可推导占位值生成；不发送真实 HTTP 请求来获取返回值。
- 参考文章的“按接口输出表格”模式组织 Word 文档，但以 OpenAPI 规范数据为唯一来源，完整保留 `path`、`query`、`header`、`cookie`、请求体和全部响应码。
- 已核对实际样例 [swagger接口文档.html](../example/swagger接口文档.html)：其“返回属性名”采用递归编号和左缩进展示响应结构树；MVP Word 导出沿用这一易读模式。

## 2. MVP 字段确认

### 2.1 字段取值与显示规则

| 输出字段 | 取值优先级或规则 |
| --- | --- |
| 接口名称 | `summary` 优先；缺失时使用 `operationId`；再缺失时使用“METHOD + PATH”。 |
| 接口标识 | 输出 `operationId`；缺失时留空，不自行生成业务名称。 |
| 接口说明 | 使用 `description`；缺失时留空。 |
| 模块 | 使用第一个 Tag 作为主分组；无 Tag 的接口归入“未分组”。 |
| Content-Type | Swagger 使用 `consumes` / `produces`；OpenAPI 使用 `content` 的媒体类型。 |
| 参数位置 | 保留 `path`、`query`、`header`、`cookie`、`body`；请求体嵌套字段标为 `body`。 |
| 必填 | 直接使用规范值；对象字段继承所属对象 `required` 列表。 |
| 示例 | `example` / `examples` 优先，其次 `default`，最后可显示类型占位值；占位值应标记为“推导”。 |
| 响应 | 输出全部定义的响应码，优先识别 `2xx` 成功响应，但不丢弃错误响应。 |

### 2.2 字段展示约束

- Word 的请求/响应字段表使用“层级序号.字段名”作为首列：根字段例如 `1.code`、`2.data`，对象子字段例如 `2.1.current`，数组元素字段例如 `2.3.1.customsCode`；每增加一层缩进一级。
- 请求体字段、响应字段和数据模型使用语义字段路径，例如 `data.records[].customsCode`；同时单列保留层级序号和父路径，便于筛选、排序和回溯。
- 数组父字段必须显示为独立行，类型显示为 `array<元素类型>`；其元素字段作为子行输出。对象父字段同样显示为独立行，类型显示为 `object<模型名>` 或 `object`。
- `$ref` 在可安全展开时展示字段；循环或超过展开深度时显示模型引用名称和“已停止展开”提示。
- `allOf` 合并可确定的字段；`oneOf` 与 `anyOf` 保留组合关系和候选模型名称，不强行合并为单一对象。
- `deprecated` 为真时，在接口清单及接口标题旁显示“已废弃”。

## 3. Word 与 PDF 结构

> PDF 不属于 MVP。本节的 Word 结构为 MVP 定稿；未来 PDF 复用相同内容结构。

### 3.1 默认章节

1. 封面：项目名称（用户填写）、API 标题、版本、生成时间。
2. 文档概述：描述、服务地址、规范版本。
3. 接口目录：Tag、接口名称、请求方法、路径。
4. 接口详情：按 Tag、路径和方法排序。
5. 数据模型附录：导出范围内关联的 Schema。

### 3.2 单接口详情（一个接口一张完整表）

- 接口标题：序号、接口名称和接口标识。
- 基本信息：接口说明、请求方法、请求路径、所属模块、弃用状态。
- 请求格式：请求 Content-Type；无请求体时显示“无”。
- 请求参数表：覆盖 `path`、`query`、`header`、`cookie` 与请求体字段。
- 响应码表：覆盖所有响应码、响应描述与响应 Content-Type。
- 成功响应字段表：优先展示首个 `2xx` 响应；若不存在 `2xx`，展示首个已定义响应并标记。
- 请求示例与成功响应示例：仅在规范或可推导值存在时展示。

### 3.3 请求参数表标准列

| 列名 | 含义 |
| --- | --- |
| 序号/字段路径 | 参数名或嵌套字段路径，例如 `items[].skuId` |
| 位置 | `path`、`query`、`header`、`cookie`、`body` |
| 类型 | 基础类型、对象、数组及 `format` |
| 必填 | 是/否 |
| 描述 | API 规范中的描述 |
| 默认值 | 默认值 |
| 枚举值 | 枚举选项 |
| 示例 | 示例值 |

### 3.4 响应码表与响应字段表

**响应码表**：状态码、响应描述、Content-Type、Schema/模型引用。  
**返回属性名表**：层级序号、字段名或字段路径、类型、必填、描述、默认值、枚举值、示例。

其中 Word 的“返回属性名”首列同时承担结构展示职责，至少应能表达以下关系：

```text
1.code
2.data                         object<Page<CustomsDistrictVO>>
	2.1.current
	2.2.records                  array<CustomsDistrictVO>
		2.2.1.customsCode
		2.2.2.customsName
3.message
```

原始样例使用 `array:模型名`、`object:模型名` 的类型文本；本产品统一使用 `array<模型名>`、`object<模型名>`，以避免冒号与类型格式混用。

### 3.5 排版规则

- 接口标题至少为三级标题，确保目录结构可识别。
- 长表格允许跨页，并重复表头。
- 代码示例使用等宽字体和自动换行。
- PDF 必须通过中文、长表格、跨页、文本复制的 PoC 验证后，才能承诺程序化 PDF 导出。

## 5. 输出质量底线

- Word/WPS、常见 PDF 阅读器可正常打开。
- 中文、英文、数字、常用标点不乱码。
- 请求方法、路径、参数必填性和响应状态码不得因转换而丢失。
- 对不能支持的规范特性应在生成日志/界面中明确提示。
- 不因示例生成而访问 API 服务器、发送鉴权信息或修改任何数据。
